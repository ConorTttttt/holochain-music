Only a named human hearing real speakers can sign an audio gate. CI runner audio/one-machine conductors cannot satisfy physical tests.

Use docs/hardware-test-plan.md for the existing Ubuntu test WAV generator, ALSA, benchmark, network commands and UI sequence; use docs/windows-lan-test-plan.md and docs/windows-wasapi-rc3.md for Windows retest details. ## Before any hardware test: validate provenance and isolate the test

Assign testers by name (not just "Agent") and use a disposable account/device or an encrypted backup before installation. Get an approved private-test package through the project owner; do not distribute publicly. Get its separately signed/published SHA-256, exact producing Git commit, build transcript, per-file hashes and hApp and bundled conductor hashes **from the same build**. If any are missing or mismatch, record **BLOCKED** and do not install. Do not overwrite another release candidate or an existing user's library to simulate failure; use a newly published track instead. Preserve grant and licence semantics.

**Ubuntu preflight (run on every machine):**

~~~bash
date -u --iso-8601=seconds
cat /etc/os-release
uname -a
lscpu | grep -E 'Model name|Architecture' || true
ip -br address
ip route
aplay -l
DEB=/absolute/path/to/THE-APPROVED-CANDIDATE.deb
sha256sum "$DEB"
dpkg-deb -f "$DEB" Package Version Architecture
dpkg-deb -c "$DEB" > package-contents.txt
~~~

Verify with approval manifest before running sudo apt install. Record whether installation is clean, upgraded or on a source-tree development host; only a clean install can satisfy H06. Record kernel, ALSA/card/device, monitor/speakers and output route. Capture complete output to a redacted log saved outside the package.

**Windows preflight (PowerShell, on actual physical hardware):**

~~~powershell
Get-Date -Format o
Get-ComputerInfo | Select-Object WindowsProductName,WindowsVersion,OsBuildNumber,OsArchitecture
Get-CimInstance Win32_ComputerSystem | Select-Object Manufacturer,Model
Get-CimInstance Win32_SoundDevice | Select-Object Name,Manufacturer,DeviceID,Status
Get-NetAdapter | Select-Object Name,Status,MacAddress,LinkSpeed
Get-NetConnectionProfile | Select-Object Name,NetworkCategory
Get-FileHash .\HolochainMusic-THE-APPROVED-VERSION-windows-x64.exe -Algorithm SHA256
~~~

Record exact Realtek/audio codec, physical speaker/headphone connection, Windows default output and sample-rate/mix format, driver name/version/date, PortAudio/sounddevice version, installation vs upgrade status, and whether SmartScreen warning appeared. Never disable Defender, SmartScreen, firewall or OS protections merely to pass.

## Gate H01 — physical Ubuntu ALSA sound

- On Ubuntu 26.04 real HP Pro Mini (or explicitly recorded substitute) validate an audible baseline with speaker-test, then publish the 30-second stereo 440 Hz left / 660 Hz right WAV generated by docs/hardware-test-plan.md Test 1; use holochain-music start --audio alsa and the actual installed application.
- Human hears the physical left/right channels and observes: correct track and Offline-ready state; play/pause/resume; keyboard ten-second seeks; seek-bar drag; volume; stop with immediate silence; restart; browser focus ring; shutdown with no leaked children.
- **Expected:** no unauthorised PCM, audible stereo, no prolonged hang/noise or timeline backwards, UI behaviour matches heard state. **Evidence:** phone recording if consented; timestamped operator notes; speaker-test and device enumeration output; full app/conductor logs with secrets removed.
- Record sound device selection (default vs hw:N,M), sink, mixer level and physical connection. A failing baseline speaker-test is an environment issue, not proof app audio works.

## Gate H02 — acoustic seek and ALSA timing

- On the same output device run packaging/bench-seek.py with --device default --seeks 20 --json seek-hw.json from the **exact source commit** that made the approved package. Record median/p95/max to first PCM write, position-backwards count and 20 output timestamps. The pre-existing plan expects timings well below 500ms; the benchmark ends at the ALSA write, **not at the ears**.
- Publish/use the existing generated 5:31 alternating silence/880-Hz audio of Test 1b. A named person performs at least 10 timed seeks from silence to tone while recording key press and *real speaker output* (phone/mic). Save waveforms/screenshots or recordings under H02/ and enumerate all measured intervals in milliseconds.
- **Expected:** no backward/stalled timeline while audio is heard, seek badge correctly tracks seeking → playing, actual sound follows promptly. Record median, maximum and all individual acoustic timings. A numerical acoustic pass threshold must be agreed by the release owner **before** the test (suggested criterion <=500ms worst, subject to device profile); do not retroactively label a result PASS.

## Gate H03 — two separate physical LAN computers

- Use machine **A = artist/host/bootstrap**, **B = listener** on an isolated private LAN. Record hostnames/models, OS/kernel/build, individual installed artifact SHA-256, NIC type and local IPs. Identify exact switched/Wi-Fi topology and firewall profile; only open the scoped host/bootstrap ports on the test LAN as in docs/hardware-test-plan.md Test 2. No public-internet exposure.
- Start fresh app processes on both machines (not two conductor instances on one computer); publish a uniquely named generated test track on A. B discovers it. Record UTC start/publish/discovery times and agent roles privately; B must have no Play action/audio while ungranted.
- B requests a **perpetual personal** licence; A explicitly approves; B sees grant, verifies badge and streams sound over MoQ/QUIC; seek while still downloading, pause/resume, then finish complete authenticated download. Record elapsed discover and request→grant times, first audible packet, stall/outage count, and listener no-PCM-before-grant evidence. If discovery exceeds 60 seconds, attach *both* conductors' debug logs rather than force PASS.
- **Expected:** no plaintext WAV or keys across the LAN, only approved listener gets access, and grant/documented transport behaviour matches. Capture a redacted packet summary if practicable, not private keys or grants.

## Gate H04 — grant denial and host outage

- **IMPORTANT current UI gap:** audited holochain_music/ui/app.js shows two Grant buttons but **no explicit Deny/Decline button or denial-notification workflow**. Therefore physically test *withholding approval* and unauthorised playback refusal, plus invalid/rate-limited request refusal, but **do not describe this as having tested an explicit interactive denial action**. Owner must decide if a visible Deny action is a release requirement; if so, mark that subgate BLOCKED and open a development issue.
- Use a new ungranted track on A. On B make a request; A does **not** approve; attempt playback/export from B. Expected: no Play when ungranted, direct playback/export refused and no PCM. Check that the request is recorded as pending, not silently granted. For malformed/rate-limited scenarios, use **disposable agents** in an isolated environment and record explicit refusal and absence of repeated outbox retries. Do not spam a production peer.
- Create a **second, new track** on A that B has licence for but has **not yet downloaded**. Stop A's host and prove B shows explicit unavailable and produces no new unauthenticated audio; restart A and test permitted recovery. A fully downloaded, already-authorised personal licence may still play offline: that is correct and **must not be counted as outage failure**.
- With artist conductor stopped, B sends a permitted request and records it queued; restart A during seven-day outbox window, wait for 30-second retry cycles, and confirm delivery and grant approval. Measure time and note retry vs permanent refusal. Do **not** delete existing CAS data or licences to fabricate an outage.
- Record queue sizes, UI state, local last-error strings (redacted), network stop/start UTC timestamps, observed playback/export result and audit reviewer sign-off.

## Gate H05 — physically disconnected offline playback and WAV export

- On B from H03 use **a fully downloaded authenticated track with a perpetual personal licence** from a different artist. Quit; unplug Ethernet, disable Wi-Fi/hotspot/cellular/tethering (physically confirm, not merely '--offline'); capture ip route, ip link and failed ping to A showing no usable network.
- Run holochain-music start --offline --audio alsa. Hear the saved track, seek/pause, export licensed WAV via UI, verify SHA-256 of exported WAV and play it using an independent ordinary player (aplay). Record audible human result. Check no unintended non-loopback sockets and no background network attempts.
- A **stream-only grant must not enable perpetual WAV export**: check refusal with a separate streaming-only test track. Do not delete the permanent licence to provoke this outcome.
- **Expected:** physically disconnected audio & exported WAV are usable under perpetual personal licence; streaming-only export refused; no network dependence. Attach offline route/ping/socket logs and WAV hash (share only generated licensed test audio).

## Gate H07 — physical Windows WASAPI audio quality, issue #26

- On Windows 11 x64 **physical Realtek** (or explicitly named alternative that does not substitute for the reported Realtek failure), install only the approved private RC3-derived candidate after checking SHA-256. Keep local profile/identity/library intact; follow docs/windows-wasapi-rc3.md and windows-lan-test-plan.md.
- Compare **the exact same authorised PCM/WAV file** through (1) the app WASAPI shared mode and (2) a normal Windows player on the *same Realtek device, connector, level and endpoint*. Test both 44.1 kHz and 48 kHz input, cold start, 5-minute uninterrupted playback, 20 seeks, 20 rapid track switches, pause/resume, stop/restart, and upgrade/uninstall retention.
- A person must record any click/crackle/pop/dropout with UTC timecode, severity, exact position and whether the reference player also reproduces it. Record device mix format, OS audio enhancements, driver, sample rate, observed stream/underrun diagnostics and logs from packaging/windows/smoke-wasapi.py when run on that hardware. A pass from the Linux scheduling model or a silent Windows Server CI host **does not close issue #26**.
- **Expected:** no recurring audible corruption during steady fully downloaded playback; reliable seeking/stop, no stale audio or unexpected rebuffer. If same WAV crackles only in app, issue #26 stays OPEN. Issue owner/human tester signs actual resolution, never Agent 4.
